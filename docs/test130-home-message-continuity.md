# test.130：首页裁切与节点切换连接保护

用户在 test.129 真机照片中反馈延迟数值下半截缺失，同时报告微信经常漏收消息。本次分别处理可以复现的布局错误与连接中断路径，不把自动化测试当作微信实机收信验证。

## 已确认的问题与修改

- 延迟卡片固定 88dp，扣除上下内边距后不足以同时容纳标题、操作按钮和数值行；实测正常字号下数值文字只得到 9px 高度，完整文字需 13px。卡片和数值行改为由内容撑开，保留最小高度；WebUI/日志快捷卡也取消固定高度，支持字体放大。
- 开启“切换节点后断开旧连接”时，两个策略入口原先都遍历整个页面连接列表。切换某个组也会断开 DIRECT 微信连接及其他组连接。现在在切换前向核心读取快照，按 `chains` 数组精确匹配当前策略组；切换成功后仅关闭匹配的旧 ID。
- 重选当前节点、关闭清理开关、未知连接链和失败的节点切换均不主动断连。清理单个连接失败不回滚已经成功的节点切换；诊断中记录本次处理数量及失败数量。
- 首页“日志”保留点击查看日志，长按可直接生成“消息与网络诊断”，便于在漏消息当时取证。

## 验证

- 生产首页组件在 320/360/412dp 宽度、1.0/1.5 字号、明暗主题下验证延迟数值与快捷卡文字垂直边界；检查真实文本布局的溢出状态和行底位置，而不只是断言文字存在。
- HTTP 模拟核心验证真实请求顺序与范围：保留微信 DIRECT、其他策略、相似名称和未知连接；只删除切换前属于当前组的连接。覆盖切换失败、重选当前节点、清理关闭以及部分删除失败。
- 首页长按诊断测试验证诊断回调触发且不误启停代理或打开日志。
- 运行边界摘要有意更新 `ProxyDashboardRepository.kt`（节点切换行为）和 `RootProxyManager.java`（仅读取新增诊断字段）；其他受保护文件保持 test.129 原值。

## 微信问题的证据边界

目前没有 test.129 漏消息当时的设备日志，也不知道该设备是否开启了节点切换断连选项。历史诊断来自旧版及启动失败阶段，不能据此确定本次根因。已修复的节点切换错误只是确定存在的中断路径，不能承诺解决锁屏限制、上游节点、源订阅规则或其他持续收信问题。

下一份所需证据：漏消息时长按首页“日志”，复制“消息与网络诊断”；注明当时是否锁屏、是否刚切换 Wi-Fi/移动数据。无需上传聊天内容。本次未改用户源 YAML、DNS 上游、规则顺序、微信分流、Root 网络脚本或保活策略。
