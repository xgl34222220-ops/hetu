# test.134：既有 TCP 连接与运行环境升级

这次修复的是可定位的连接中断路径，不把它当作用户手机所有微信延迟的已确认根因。

## TPROXY 启动时保留既有连接

此前 `install_mangle4/6` 对应用的全部 TCP 数据包打 mark，包括代理启动前已经和远端建立的连接。已有连接的 ACK/数据会被改送到新建的透明监听器；监听器没有原连接的握手和序列号状态，无法把它接续为代理连接。这会使消息通道等长连接中断，直到应用自行重连。

现在用当前会话分配的私有 connmark 位记录由河图接管的 TCP 流：

- 已建立且没有该位的旧 TCP 流继续原路径。
- 新接管的 TCP 流写入该位，后续 ACK/数据仍经 TPROXY，不是把全部已建立连接放行。
- 仅更新私有 bit，保留其他防火墙的 connmark；IPv4、IPv6 和共享入口使用相同原则。
- DNS 的独立 NAT 接管、UDP、应用选择及显式绕过规则不改。
- 热修复仍按现有会话的规则快照恢复。升级不会半途给旧核心安装新的连接判定规则。
- TCP conntrack/connmark 功能在首次预检验证；预检缓存包含运行环境修订号。

## 修复需要真正安装到运行会话

APK 替换后原 Root 核心和脚本继续运行。旧逻辑无条件清除待升级状态，容易使新 APK 的修复一直没有部署。

现在 `ProxyRuntimeSettings.RUNTIME_REVISION` 与成功启动时记录的修订号比较。仅运行环境变化才提示，纯 UI 更新不提示。广播漏收时也可从已应用修订号识别旧会话。只在用户明确启动/重启且网络事务成功后记录新修订号；配置热重载不能把未部署的脚本标为完成。没有自动重启、批量关闭连接或新增微信全应用直连规则。

## 回归

- `RuntimeUpgradeTest`：旧核心升级保持运行且不启动服务、修订号相同不制造重启、漏广播/配置重载不隐藏脚本升级。
- `ProxyRuntimeSettingsTest`：停机、旧版本、当前版本、持久待应用和更高修订号。
- `test_tcp_startup_continuity.py`：隔离的真实 Linux 网络命名空间中比较旧算法和新规则，验证代理启动前后持续的 TCP 请求/应答、新建代理流、私有 mark、DNS 与应用范围。需要有网络命名空间权限的 CI 环境。
- 现有规则/路由恢复、IPv6、可选 IPv6 NAT 和生命周期测试继续运行。

Linux 网络回归和模拟配置不能替代用户手机的锁屏、厂商省电策略、运营商网络切换与微信实测。安装本版后需在首页主动执行一次「重启代理并应用修复」，让旧 Root 会话使用新脚本。
